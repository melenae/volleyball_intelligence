# Подтверждённая архитектура

Статус: принято перед Phase 1. Модели, аналитика и seed в этой фазе не реализуются. Документ фиксирует правила, которым должны следовать следующие фазы.

## Источник данных

PostgreSQL — единственный источник для экранов и расчётов. Demo-данные, будущий импорт файла и будущий AVL только записывают строки в каноническую модель. Аналитический запрос не обращается к внешнему API.

Внутренний первичный ключ — UUID. Внешний идентификатор не становится первичным ключом.

## Доступ к базе и контракты

SQLAlchemy 2 используется с синхронными сессиями. В Phase 1 создан только engine для проверки `SELECT 1`. ORM-моделей нет.

Публичный контракт описывается OpenAPI и Pydantic-схемами. Отдельный пакет shared-contracts не заводится, пока у API один потребитель — приложение `apps/web`.

API первой версии только читает данные. Загрузка demo-данных будет CLI, не HTTP-методом. Авторизация не добавляется, пока не появится запись через HTTP.

Браузер ходит в Next.js по относительному `/api/...`. Сервер Next.js проксирует запрос в FastAPI. CORS на API разрешает только список `CORS_ORIGINS`, без `*` и без credentials.

## Язык и происхождение данных

Интерфейс и документация — на русском. Идентификаторы в коде — на английском.

Ответы с показателями лиги помечаются `data_origin: "demo"`. Health endpoint эту пометку не ставит: в Phase 1 данных лиги нет.

## Матч: стороны и площадка

У матча явно хранятся `home_team` и `away_team`. Это две стороны протокола, а не утверждение, что матч проходит в зале одной из них.

`venue` может быть пустым. Пустая площадка означает нейтральную площадку и не влияет на победителя.

`home_team` и `away_team` обязательны и должны различаться.

## Какие матчи входят в статистику завершённых корректных матчей

Победитель определяется только по результатам сетов. Приложение не назначает победителя автоматически, если результаты неполные или противоречивые, и не включает такой матч в статистику завершённых корректных матчей.

Матч входит в эту статистику только когда выполнены все условия:

1. `status` равен `completed`.
2. Обе стороны заданы и различаются.
3. Есть хотя бы один сет.
4. Номера сетов — целые числа от 1, уникальны и образуют непрерывный диапазон `1..N` без пропусков.
5. В каждом сете оба счёта — целые числа `>= 0` и не равны друг другу.
6. Победитель сета — сторона с большим счётом в этом сете.
7. Победитель матча — сторона, выигравшая строго больше сетов.

Если число выигранных сетов совпало, результат противоречивый: победитель не назначается, матч исключается.

Исключаются также матчи со статусом `scheduled` или `cancelled`, матчи без сетов, с ничейным сетом, с пропуском или повтором номера сета, с отсутствующим счётом и с одинаковыми сторонами. Отдельные сеты не выбрасываются, чтобы искусственно получить победителя. Исключается весь матч.

Число сыгранных матчей, победы, поражения, сеты, очки и процент побед считаются только по таким корректным завершённым матчам. При нуле подходящих матчей процент побед равен `null`, а не `0`.

Очки — сумма записанных счетов сетов. Счёт не пересчитывается из розыгрышей и не проверяется на правило «победа в сете с разницей в два очка».

Эти правила покрываются тестами вместе с моделью матча и модулем аналитики. В Phase 1 тестов предметной области нет, потому что сущностей ещё нет.

## Идемпотентный seed

Повторный запуск seed вымышленных demo-данных не создаёт дубликаты. Реализация появится вместе с моделью. Ожидаемые естественные ключи:

- лига: `slug`;
- сезон: лига + имя сезона;
- команда: `slug`;
- игрок: стабильный `demo_slug` из фикстуры, не отображаемое имя;
- состав: команда + игрок + сезон;
- матч: сезон + `scheduled_at` + хозяева + гости; у каждого demo-матча `scheduled_at` задан;
- сет: матч + номер сета.

Повторный запуск находит существующие строки по этим ключам. Совпадение ключа с другим содержимым обновляет строку или оставляет её, но не вставляет вторую. Два разных матча с одним ключом — ошибка seed, а не две записи. Тест второй фазы проверяет, что повторный запуск не меняет число строк.

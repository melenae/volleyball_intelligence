# Происхождение данных (`data_origin`) и модель провенанса

**Status:** Proposed  
**Дата:** 2026-10-15  
**Связанные документы:** [0001-confirmed-architecture.md](./0001-confirmed-architecture.md), [Phase 7 Step 1](../phase7/step1-real-data-source-contract-discovery.md), [0003-ingestion-runs-journal.md](./0003-ingestion-runs-journal.md)

---

## Context

Сегодня все аналитические ответы API и UI получают `data_origin: "demo"` из Pydantic-схем (`WithDataOrigin`, значение по умолчанию `"demo"`), независимо от того, как строки попали в PostgreSQL: demo-seed, strict JSON import (`source=file` в `ingestion_external_keys`) или ручные тестовые загрузки.

Компонент `DemoBadge` в `apps/web` показывает предупреждение только при `dataOrigin === "demo"`; любое другое значение сейчас **скрывает** badge целиком, хотя отдельного UX для «реальных» данных нет.

Канонические сущности (`leagues`, `seasons`, `teams`, `players`, `matches`, …) **не хранят** происхождение. Таблица `ingestion_external_keys` фиксирует связь внешнего id с UUID и поля `source` / `bundle_ref`, но:

- demo-seed **не** создаёт external keys;
- одна глобальная команда или игрок может теоретически фигурировать в матчах разных «пакетов»;
- API не читает `ingestion_external_keys` для формирования `data_origin`.

Контракт AVL **не подтверждён**; решения ниже должны работать для demo, file import и будущего адаптера без предположений о полях AVL.

---

## Decision Drivers

- Пользователь и оператор должны **не путать** демо, файл и (в будущем) официальный источник.
- Аналитика и UI должны опираться на **однозначный контекст сезона/лиги**, в котором строится отчёт (dashboard, standings, timeline).
- Минимизировать ложные выводы из текущего API: `data_origin: "demo"` **не является** достоверным признаком происхождения записей в БД.
- Сохранить UUID как внутренний ключ; не делать внешний id первичным ключом ([0001](./0001-confirmed-architecture.md)).
- Обратная совместимость для клиентов, которые уже парсят `data_origin` (расширение enum предпочтительнее удаления поля).
- Согласованность с журналом импорта ([0003](./0003-ingestion-runs-journal.md)): происхождение пакета и run должны быть сопоставимы.

## Considered Options

### Option A — Поле происхождения на каждой сущности

На каждой доменной таблице (или на подмножестве) колонки вида `data_origin`, опционально `source_label`, `ingestion_run_id`.

| | |
|--|--|
| **Плюсы** | Точная маркировка строки; простые SQL-фильтры «только demo». |
| **Минусы** | Дублирование; неясность при shared entity (один `teams` в demo и imported матчах); дорогая миграция всех таблиц; риск рассинхрона полей внутри одного матча (сезон imported, команда demo). |
| **Demo + imported** | Требуются жёсткие правила: либо запрет shared teams/players, либо «происхождение сущности» ≠ «происхождение контекста просмотра». |
| **Аналитика / UI** | Можно помечать каждую строку списка; для dashboard всё равно нужен агрегирующий контекст (сезон). |
| **Миграция** | Backfill всех строк; demo-seed → `demo`; imported → по external keys (сложно для строк без keys). |
| **API** | Расширение `TeamRead` и т.д.; breaking, если клиенты не ожидают новых полей (обычно additive OK). |

### Option B — Происхождение на уровне импортированного набора (scope: лига / сезон)

Явные поля на `leagues` и/или `seasons`: `data_origin` (enum), `source_code` (`file`, будущий `avl`, …), `source_label` (например `source_label` из JSON v1), опционально `primary_ingestion_run_id`.

| | |
|--|--|
| **Плюсы** | Соответствует UX («сезон 2024/25 — данные AVL»); мало таблиц; demo-seed помечает одну demo-лигу/сезоны без external keys. |
| **Минусы** | Не описывает shared глобальные `teams`/`players` вне сезона; смешение в одной БД (demo + pilot JSON) требует дисциплины slug или отдельных лиг. |
| **Demo + imported** | Разные сезоны/лиги — разные значения; коллизии slug между demo и import остаются проблемой ingestion (не этого ADR). |
| **Аналитика / UI** | `data_origin` в ответе API выводится из **выбранного сезона** (query param / dashboard season), а не константа. |
| **Миграция** | Demo-лига: `demo`; сезоны без импорта — `demo`; импортированные сезоны — по `bundle_ref` / run. |
| **API** | Расширить `DataOrigin` literal; логика в сервисах чтения; **поведение по умолчанию для старых клиентов:** документировать, что `"demo"` больше не означает «все данные вымышленные», если не выбран demo-сезон. |

### Option C — Отдельная модель происхождения / привязки

Таблица(и) `data_provenance` или `entity_provenance`: `(entity_type, internal_id) → origin_kind, source, bundle_ref, run_id, valid_from`.

| | |
|--|--|
| **Плюсы** | Гибкость; история смены источника; несколько записей provenance на сущность (редкий случай). |
| **Минусы** | Сложность запросов и JOIN; без чёткой политики быстро станет неподдерживаемой. |
| **Demo + imported** | Можно моделировать «игрок создан demo, roster imported», но API должно определить, что показывать. |
| **Аналитика / UI** | Требует resolver-слой; риск расхождения с «простым» badge на сезоне. |
| **Миграция** | Backfill из `ingestion_external_keys` + правило для demo. |
| **API** | Новые поля или вложенный объект provenance; больше всего изменений в контракте. |

### Option D — Вывод только из `ingestion_external_keys` (без колонок происхождения)

`data_origin` и label вычисляются при чтении: есть ключ с `source=file` → `imported`; нет ключей → `demo`.

| | |
|--|--|
| **Плюсы** | Нет дублирования; уже есть `source` и `bundle_ref`. |
| **Минусы** | Demo-seed не оставляет ключей — эвристика «нет ключей = demo» ломается для старых import-only БД; ambiguous для entity с несколькими ключами (не должно быть при unique constraint, но shared internal_id из разных bundle — отдельный вопрос); сезон без единого bundle_ref при нескольких импортах. |
| **Demo + imported** | Плохо разделяет demo-лигу и imported-лигу, если обе без ключей на league row. |
| **Аналитика / UI** | Нестабильный badge при неполных ключах. |
| **Миграция** | Минимальная в БД, максимальная в коде resolver. |
| **API** | Скрытая логика; сложно тестировать и объяснить потребителю. |

### Option E — Комбинация B + ограниченный C

**Канон для UX и API (направление):** происхождение на уровне **сезона** (и при необходимости лиги): enum + метаданные пакета.  
**Опционально:** `ingestion_external_keys.ingestion_run_id` (см. [0003](./0003-ingestion-runs-journal.md)) для трассировки, без дублирования origin на каждой строке `matches`.  
**Shared сущности:** глобальные `teams`/`players` без собственного `data_origin` в первой итерации; badge по **контексту сезона** запроса.  
**Смешение demo и imported в одном сезоне** — не решено в существующих требованиях; см. раздел «Семантика `seasons.data_origin` и смешение источников».

| | |
|--|--|
| **Плюсы** | Баланс простоты и честности; стыкуется с run journal; demo-seed остаётся простым. |
| **Минусы** | Нужны продуктовые правила для edge cases (игрок в двух сезонах с разным происхождением). |
| **Demo + imported** | Разные сезоны — разные badges; одна БД допустима при разных slug/лигах. |
| **Аналитика / UI** | Dashboard/standings по `season_id` → один `data_origin` на ответ. |
| **Миграция** | Колонки на `seasons` (и опционально `leagues`); backfill demo. |
| **API** | Расширение enum; deprecated семантика «всегда demo». |

## Семантика `seasons.data_origin` и смешение источников

### Что означает поле на сезоне (не утверждено — варианты интерпретации)

Если provenance хранится на `seasons`, необходимо явно зафиксировать **семантику** `data_origin` (и связанных полей). Возможные модели:

| Модель | Смысл `seasons.data_origin` | Когда уместна |
|--------|------------------------------|---------------|
| **S1 — Источник всего сезона** | Одно значение описывает **все** доменные строки, привязанные к сезону (матчи, roster, косвенно команды/игроки в UI этого сезона). | Один ingestion-пакет на сезон; запрет или исключение смешения. |
| **S2 — Основной / канонический источник** | Значение описывает **доминирующий** источник (например официальная лига), но отдельные строки могли появиться иначе. | Нужен badge «от лица лиги», детали — в ops. |
| **S3 — Источник исходного набора** | Значение фиксирует **первый успешный** пакет, создавший сезон; последующие import не меняют origin без политики update. | Strict writer, идемпотентные повторы; плохо при смене официального поставщика. |
| **S4 — Не сезон, а набор данных** | На сезоне поле отсутствует или `unknown`; provenance на уровне **пакета / run** (связь с [0003](./0003-ingestion-runs-journal.md)) или сущности (Option A/C). | Несколько bundle на один сезон; mixed-origin по дизайну. |

**Текущий репозиторий не задаёт** ни S1–S4. До выбора владельцем продукта реализация **не должна** автоматически выставлять `imported` при успешном file import только потому, что пакет прошёл writer ([согласованность с 0003](#согласованность-с-журналом-импорта-0003)).

### Demo и imported в одном сезоне

Фактически возможные ситуации (даже без злого умысла):

- demo-seed и позже JSON import в **ту же** лигу/сезон (коллизия natural keys / slug);
- общие глобальные `teams`/`players`: матчи demo-сезона и imported-сезона ссылаются на один UUID;
- ручные правки в БД + import.

**Варианты политики (выбор — продукт):**

| Политика | Поведение | Плюсы | Минусы |
|----------|-----------|-------|--------|
| **P1 — Запрет смешения** | Ingestion/writer отклоняет пакет, если сезон уже `demo` (или наоборот); один сезон — один класс источника. | Простой badge; совпадает с S1. | Жёстко для миграции demo → real; отдельный сезон/лига для пилота. |
| **P2 — Явный `mixed` / `unknown`** | Расширить enum значением `mixed` (или `unknown`), выставлять при детекции конфликтующих признаков (keys + demo flag, ops rule). | Честность перед пользователем. | Нужны правила детекции; аналитика «как demo или как real?». |
| **P3 — Provenance на сущности или пакете** | `seasons.data_origin` не используется или вторичен; badge из run/bundle или полей на `matches`/наборах (Option A/C, S4). | Точность при смешении. | Сложность API/UI; больше миграций. |

**Вопрос владельцу продукта:** допускается ли в **одном сезоне** одновременное присутствие demo- и import-происхождения (да/нет)? Если да — badge сезона должен показывать `mixed`/детализацию (P2) или provenance только на уровне матча/пакета (P3)? Если нет — подтверждаем P1 и семантику S1/S3?

### `source_code`, `source_label` и external keys

| Понятие | Уровень | Назначение | Пример |
|---------|---------|------------|--------|
| **`ingestion_external_keys.source`** | Строка mapping | Технический код **канала** идентичности (`file` сегодня; в будущем отдельная константа адаптера после контракта). Участвует в уникальности `(source, entity_type, external_id)`. | `file` |
| **`ingestion_external_keys.external_id`** | Per entity | Стабильный id сущности **внутри канала** (в JSON v1 = `ref` пакета). | `season-2025` |
| **`ingestion_external_keys.bundle_ref`** | Per key (пакет) | Метка **пакета импорта**, из которого пришла привязка (`source_label` JSON v1). Не заменяет external_id. | `pytest-import-valid` |
| **`seasons.source_code`** (предлагаемое) | Per season | Дублирует или обобщает **канал** для UX/ops на уровне сезона; может совпадать с `ingestion_external_keys.source` первого пакета. | `file` |
| **`seasons.source_label`** (предлагаемое) | Per season | Человекочитаемая/операционная метка **пакета или поставщика** для badge и run journal; часто = `bundle_ref`. | `phase6-pilot-e2e` |
| **`seasons.data_origin`** (предлагаемое) | Per season | **Продуктовый** класс происхождения для API/UI (`demo`, `imported`, зарезервированное `avl`). Не равен `source` в external keys без явной таблицы соответствия. | `imported` |

External keys отвечают на **сопоставление id**; поля сезона — на **как показывать и интерпретировать контекст**, после утверждения семантики S* и политики P*.

### Значение `avl` в enum (не реализованный источник)

- `avl` в enum — **зарезервированное** будущее значение для продуктового класса «официальный подключённый поставщик AVL».
- До **подписанного контракта**, credentials и приёмки адаптера: **нет** live-заполнения `data_origin=avl` из кода; **нет** документации, утверждающей, что AVL уже подключён.
- В UI/API текст для `avl` допустим в спецификации копирайта, но feature flag / отсутствие данных с `avl` в prod до go-live.
- Run journal: код `source` для адаптера — отдельная константа в `ingestion.constants`, вводится **вместе с** адаптером, не раньше ([0003](./0003-ingestion-runs-journal.md)).

### API и UI: откуда брать provenance после внедрения

Provenance в ответах должен исходить из **канонических данных** (колонки `seasons` / будущие таблицы), а не из константы в Pydantic-default.

| Потребитель | Сегодня | Целевое (после реализации, при принятии ADR) |
|-------------|---------|-----------------------------------------------|
| `apps/api/app/schemas/api_responses.py` — `WithDataOrigin` на list/detail/analytics | default `"demo"` | Значение из **сезона контекста** запроса (или явный `unknown` до backfill) |
| Эндпоинты с season scope: dashboard, standings, team analytics, matches list/filter by season | то же | `season_id` → load `Season` → `data_origin`, опционально `source_label` |
| Эндпоинты без season (например список всех teams/players) | `"demo"` | **Открытый вопрос:** season-agnostic listing vs nullable provenance vs привязка к «текущему» сезону UI |
| `apps/web/src/types/api.ts` — `DataOrigin` | только `"demo"` | Расширение union + опционально `mixed`/`unknown` по продукту |
| `apps/web/src/components/demo-badge.tsx` | badge только для `demo` | Обобщённый компонент источника; тексты из provenance сезона |
| Страницы: `dashboard-view`, `teams/page`, `teams/[id]`, `players/*`, `matches/*` | передают `data_origin` с API | без изменения маршрутов; данные с сервера |
| `docs/api.md`, тесты `test_api.py` | ожидают `"demo"` | обновление после утверждения семантики |

Health endpoint — **без** `data_origin` (без изменений).

## Proposed Decision

**Направление (Proposed, не Accepted):** склоняться к **Option E** — provenance на **сезоне** + трассировка через external keys / ingestion runs, **после** закрытия продуктовых вопросов S* и P*.

1. **Хранение (черновик схемы):** на `seasons` (минимум) поля `data_origin`, `source_label`, `source_code` — семантика по таблицам выше; nullable / `unknown` до backfill и до политики присвоения при import.

2. **Присвоение при import:** успешный file import **сам по себе** не обязывает выставлять `imported`, пока владелец продукта не утвердит связку «успех run + создание сезона из пакета → значение origin» (см. [0003](./0003-ingestion-runs-journal.md)).

3. **API:** убрать константный default как единственный источник правды; читать provenance из БД по контексту сезона. Health без изменений.

4. **UI:** эволюция `DemoBadge` → отображение класса источника из API; `avl` только когда данные реально помечены так после go-live.

5. **Не** вводить per-row `data_origin` на `matches`/`players` в первой итерации, **если** выбраны P1 или S1/S3; при P3 — пересмотреть.

6. External keys — **идентичность**; journal runs — **попытки загрузки**; ни то ни другое не заменяет продуктовую семантику без решения S*.

До **Accepted** ADR и отдельного решения по P*: текущее API-поведение (`data_origin: "demo"` везде) сохраняется.

## Consequences

### Positive

- Пользователь видит корректный источник для выбранного сезона.
- Demo-seed явно помечается без external keys.
- После утверждения политики — явное присвоение provenance при создании сезона из пакета (отдельная задача writer, не автоматически из этого ADR).
- Согласование с `ingestion_runs`: run ссылается на тот же `source_label` / `bundle_ref`.

### Negative / risks

- Клиенты, интерпретировавшие `data_origin: "demo"` как «вся БД demo», получат **семантическое** изменение (breaking на уровне смысла, не обязательно на уровне JSON schema).
- Shared `teams`/`players` между demo и imported сезонами могут визуально «наследовать» badge сезона, а не «происхождение игрока» — нужна документация продукта.
- Потребуется обновить тесты API и frontend (`DataOrigin` union, badge tests).

### Analytics

- Агрегаты по сезону остаются корректными; при смешении valid/invalid матчей происхождение не заменяет `evaluate_match_result`.
- Сравнение demo vs real лиг — через выбор сезона, не через глобальный флаг API.

## Migration Plan

1. **ADR accepted** → миграция Alembic: колонки на `seasons` (и при необходимости default на `leagues`).
2. **Backfill:** все сезоны demo-лиги из seed → `data_origin=demo`, `source_label` null или фиксированное `demo-seed`.
3. **Imported сезоны:** для существующих данных — SQL по связи season ↔ `ingestion_external_keys` (`entity_type=season`) и `bundle_ref`; при отсутствии ключа — ручной runbook или повторный dry-run/import не выполнять без ops.
4. **API:** сервисный слой загружает сезон, прокидывает `data_origin` в `WithDataOrigin`; удалить default-only `"demo"` для эндпоинтов, зависящих от season.
5. **Frontend:** типы, badge, тесты.
6. **Документация:** обновить `docs/api.md`, `AGENTS.md`, [0001](./0001-confirmed-architecture.md) — уточнить, что пункт про `data_origin: "demo"` относится к demo-**контексту**, не к глобальной константе (после внедрения).

Откат: оставить колонки nullable + вернуть константу в API (feature flag), если потребуется.

## Open Questions

1. **Семантика сезона:** S1, S2, S3 или S4 (см. выше)?
2. **Смешение в одном сезоне:** P1, P2 или P3 — и главный вопрос владельцу продукта (раздел «Demo и imported в одном сезоне»).
3. Достаточно ли **сезона** как scope, или лига тоже должна нести `data_origin`?
4. Нужен ли отдельный origin для **file import в dev** vs **production** официального канала, или достаточно `imported` vs зарезервированного `avl`?
5. Политика при **нескольких успешных import** в один сезон (один `source_label`, последний run, или S4)?
6. Показывать ли `source_label` в UI или только в ops?
7. Сезоны без ingestion (ручная БД): `unknown`, запрет, или ops-only?
8. Фильтрация списка сезонов в UI по `data_origin`?
9. Provenance для **season-agnostic** list endpoints (teams/players)?

## Согласованность с журналом импорта (0003)

| Сценарий | Поведение |

| Demo seed | Может выставить `data_origin=demo` при реализации; run по умолчанию **не** создаётся (см. 0003). |

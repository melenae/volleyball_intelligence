## 1. Текущие возможности проекта

### Архитектура и границы

- Модульный монолит: `apps/api` (FastAPI, SQLAlchemy, Alembic), `apps/web` (Next.js 16, read-only UI).
- PostgreSQL — единственный источник для экранов и аналитики; внешние адаптеры только **записывают** в каноническую модель ([`docs/decisions/0001-confirmed-architecture.md`](../decisions/0001-confirmed-architecture.md)).
- Внутренние ключи сущностей — UUID. Секреты — только в переменных окружения.

### Каноническая модель (Phase 2)

| Сущность | Ключевые поля и ограничения |
|----------|-----------------------------|
| `leagues` | `name`, уникальный `slug` |
| `seasons` | `league_id`, `name`, `start_date`, `end_date`; уникальность `(league_id, name)` |
| `teams` | `name`, уникальный `slug`, опционально `logo_url` (глобальная команда, не привязана к лиге в схеме) |
| `players` | `demo_slug` (уникальный), `first_name`, `last_name`, `display_name`, опционально `position` |
| `team_rosters` | `(team_id, player_id, season_id)` уникально; `jersey_number`, `active_from`, `active_until` |
| `matches` | `season_id`, `home_team_id` ≠ `away_team_id`, `status`, опционально `scheduled_at` (timestamptz), `venue` |
| `set_results` | `(match_id, set_number)` уникально; неотрицательные счёта, без ничьи в сете |

Статусы матча: `scheduled`, `completed`, `cancelled` ([`docs/data-model.md`](../data-model.md), [`docs/match-result-validity.md`](../match-result-validity.md)).

Корректность результата для агрегатов — отдельно от статуса `completed`: правила в `app/services/match_result.py` (непрерывные номера сетов, победитель по большинству сетов, без ничьей в сетах). Правило «+2 в сете» **не** проверяется.

### Демо-данные

- CLI: `python -m app.ingestion.demo.seed` — идемпотентный **upsert** по фикстурам, **без** `ingestion_external_keys`.
- Не являются данными AVL.

### Импорт JSON v1 (Phase 5)

- Документация: [`docs/ingestion/file-format-v1.md`](../ingestion/file-format-v1.md).
- Только CLI (`python -m app.ingestion.cli`), **не** HTTP API.
- Один файл — одна лига, связи через `*_ref`; `source_label` → `bundle_ref` в `ingestion_external_keys`.
- Источник ключей: `source=file` ([`app/ingestion/constants.py`](../../apps/api/app/ingestion/constants.py)).
- `players[].ref` сохраняется в `players.demo_slug`.
- Режим **strict**: повторный импорт с теми же данными — skip; расхождение полей — `data_conflict`; коллизия slug/demo_slug без mapping — `slug_conflict` / `natural_key_conflict` / `ambiguous_match`.
- **Нет** сценария «обновить поле в БД из нового пакета» — только create или полное совпадение.
- `validate` — структура и ссылки в файле; конфликты с БД — `import --dry-run`.
- Транзакция: при ошибке или `--dry-run` — `rollback`; при успехе — один `commit` на весь пакет.
- `summary` — агрегация по `ingestion_external_keys`, **не** журнал запусков (время, оператор, ошибки по шагам).

### Внешние ключи импорта

Таблица `ingestion_external_keys`: `(source, entity_type, external_id)` → `internal_id`, опционально `bundle_ref`.  
Типы: `league`, `season`, `team`, `player`, `match`, `roster` (roster: `team_ref|player_ref|season_ref`).

### AVL

- Заглушка: [`docs/ingestion/avl-adapter-placeholder.md`](../ingestion/avl-adapter-placeholder.md), код `apps/api/app/ingestion/avl/placeholder.py` (`AvlImportDataSource.load_bundle()` → `NotImplementedError`).
- Протокол будущего адаптера: `ImportDataSource.load_bundle() -> ImportBundleV1` — нормализация в тот же writer, что и файл.

### API и UI

- Read-only REST (`docs/api.md`): сезоны, команды, игроки, матчи, dashboard, standings, team timeline.
- Все аналитические ответы: `data_origin: "demo"` (константа в схемах; **не** зависит от способа загрузки данных в БД).
- UI: `DemoBadge` на экранах с `data_origin`.
- Индивидуальная матчевая статистика игрока **не** рассчитывается (нет `MatchEvent`).

### Проверки качества (уже есть)

- Pydantic-схема `ImportBundleV1`, структурная валидация, pytest (в т.ч. pilot fixture `pilot_phase6_bundle.v1.json`).
- **Phase 6 (ограниченный синтетический пилот):** в рамках проекта проведена приёмка (тесты, CLI/API/UI на synthetic bundle); вердикт — готовность к **ограниченному** пилоту на вымышленных данных, не к production и не к AVL. Отдельного acceptance-документа или ADR в репозитории нет — статус следует из артефактов (fixture, покрытие pytest) и зафиксированной приёмки, а не из отдельного файла `docs/`.

## 2. Подтверждённые факты и неподтверждённые предположения

### Сводная таблица

| Категория | Подтверждено в репозитории | Известно о AVL (только из placeholder-документа) | Неизвестно / нужно запросить у владельца AVL | Нельзя считать подтверждённым |
|-----------|----------------------------|--------------------------------------------------|-----------------------------------------------|-------------------------------|
| **Приём данных** | JSON v1 через CLI; strict writer; external keys для `source=file` | После контракта — адаптер → тот же `ImportBundleV1` | Формат API/файла AVL, кодировки, версионирование | Что AVL отдаёт JSON или REST; структура полей |
| **Доступ** | Нет HTTP-клиента, токенов, URL | Нужны: тип auth, sandbox/prod, rate limits | Базовый URL, endpoints, квоты, ToS, IP allowlist | Любые конкретные URL, методы, заголовки |
| **Идентификаторы** | Внутри файла — `ref`; в БД — UUID + optional external_id | Нужны стабильные внешние id по типам сущностей | Правила смены id, merge/split команд и игроков | Соответствие AVL id ↔ нашим `ref` или slug |
| **Лига/сезон** | Одна лига на пакет; сезон в лиге по имени | — | Несколько лиг в одном потоке; вложенность турниров | Имена сезонов AVL уникальны в рамках лиги |
| **Команды** | Глобальный `slug` | — | Ребрендинг, дубликаты названий, логотипы CDN | Команда в AVL = одна запись `teams` на все сезоны |
| **Игроки** | `demo_slug` = `ref` в файле | — | Смена фамилии, дубликаты, privacy | Поле `position` совпадает с классификацией AVL |
| **Составы** | Тройка team+player+season; номер и даты активности | Привязка к сезону, номер | Трансферы mid-season, loan, список без матчей | Семантика `active_from`/`active_until` в AVL |
| **Матчи** | home/away, 3 статуса, venue nullable | Статусы, TZ, отмены/переносы | live/in_progress, walkover, технические результаты | Часовой пояс в источнике и политика DST |
| **Сеты** | Целые счёта, без ничьи; произвольное N сетов | Формат счёта | Golden set, отменённые сеты, правки постфактум | AVL всегда отдаёт полный набор сетов для `completed` |
| **Правовое** | Demo не AVL | Разрешение на копирование в PostgreSQL и показ в продукте | Лицензия, атрибуция, срок хранения | Устное «можно парсить сайт» |
| **Происхождение в UI** | Везде `data_origin: "demo"` | — | Как маркировать реальную лигу | Импортированные пакеты уже видны как «demo» в API |

**Вывод:** официального контракта AVL в репозитории **нет**. Реализация live-интеграции **заблокирована** до передачи спецификации, образца данных и согласованных правил доступа.

## 3. Требования к контракту данных

Для каждой сущности — что нужно **минимум** для текущей модели + **вопросы** к источнику.

### Лига и сезон

| Нужно для импорта v1 | Вопросы к AVL |
|----------------------|----------------|
| Лига: `ref`, `name`, `slug` | Стабильный внешний id лиги; правила slug; несколько соревнований |
| Сезон: `ref`, `name`, `start_date`, `end_date`, `league_ref` | Границы сезона (календарь vs плей-офф); переименование сезона |

### Команды

| Нужно | Вопросы |
|-------|---------|
| `ref`, `name`, `slug`, опционально `logo_url` | Стабильность id при смене названия; URL логотипа и hotlinking; одна команда в нескольких лигах |

### Игроки

| Нужно | Вопросы |
|-------|---------|
| `ref`, `first_name`, `last_name`, `display_name`, опционально `position` | Уникальность id; отображаемое имя vs официальное; запрет публикации ПДн |

### Составы (`team_rosters`)

| Нужно | Вопросы |
|-------|---------|
| `team_ref`, `player_ref`, `season_ref`, опционально `jersey_number`, `active_from`, `active_until` | Полный roster vs только игравшие; смена номера; уход из состава — удаление строки или end date |

### Матчи

| Нужно | Вопросы |
|-------|---------|
| `ref`, `season_ref`, `home_team_ref`, `away_team_ref`, `status`, опционально `scheduled_at`, `venue`, `sets` | Определение home/away; перенос (тот же `ref`?); статусы кроме трёх; матч без даты; нейтральная площадка |

### Результаты сетов

| Нужно | Вопросы |
|-------|---------|
| Для `completed`: `set_number`, `home_score`, `away_score`; для `scheduled`/`cancelled` — пустой `sets` | Частичный результат; исправления счёта; соответствие аналитическим правилам `match_result` |

### Внешние идентификаторы и стабильность

- Контракт должен явно задать: тип id (строка/число), неизменность во времени, поведение при merge.
- Для AVL-адаптера потребуется решение: `source=avl` (или иной код) и mapping в `ingestion_external_keys` **вне** поля `ref` файла (сейчас `external_id` = `ref` из пакета).
- Согласовать связь внешнего id с `slug` / `demo_slug` (коллизии с demo-seed и между лигами).

### Даты, время, timezone

- В БД: `matches.scheduled_at` — `DateTime(timezone=True)`.
- JSON v1: `datetime` без отдельного поля TZ — **нужно правило**: UTC, offset в строке, или локаль площадки.
- Вопросы: меняется ли `scheduled_at` при переносе; история старых слотов.

### Пропуски, исправления, отмены

- Текущий импорт: **нет** delete; **нет** patch — только идемпотентный skip или `data_conflict`.
- Контракт должен описать: как сообщать об исправлении счёта, отмене после `completed`, удалении матча из источника.

### Поля, которые модель **не** поддерживает (безопасный импорт невозможен без расширения)

| Область | Примеры |
|---------|---------|
| События матча | `MatchEvent`, статистика игрока в матче |
| Происхождение в БД | `data_origin` на уровне лиги/сезона/записи |
| Журнал импорта | run id, checksum, оператор, длительность |
| Статусы матча | `in_progress`, `postponed`, `forfeit` как отдельные значения |
| Турнирная сетка | раунд, группа, стадия, номер тура |
| Персонал | тренеры, судьи |
| Расширенный профиль | фото, рост, гражданство, дата рождения |
| Standings от источника | очки, бонусы, штрафы вне расчёта из матчей |
| Версионирование | history таблицы, soft delete, source revision |
| Связь команда–лига | отдельная регистрация команды в лиге (сейчас только через матчи/roster) |

## 4. Архитектурные решения и trade-offs

*Только для обсуждения; реализация — после отдельного согласования.*

### 4.1. `data_origin` в API и UI

| Вариант | Плюсы | Минусы |
|---------|-------|--------|
| A. Константа `"demo"` как сейчас | Нет изменений | Вводит в заблуждение при реальных данных |
| B. Поле на лиге/сезоне в БД, API отдаёт из контекста запроса | Точная маркировка | Миграция, правила при смешанных источниках в одной БД |
| C. Вывод из `ingestion_external_keys.source` / `bundle_ref` | Без дублирования | Сложно для demo-seed без ключей; неочевидно для старых данных |
| D. Enum: `demo` \| `imported` \| `avl` + опциональный `source_label` | Прозрачно для UI badge | Нужна продуктовая копия и фильтры |

**Рекомендация для обсуждения:** D на уровне **сезона или лиги** (пользовательский контекст), с явным правилом для demo-seed (`demo`) и AVL (`avl` + метка). UI: расширить `DemoBadge` → нейтральный «Источник данных».

### 4.2. История запусков импорта

| Вариант | Плюсы | Минусы |
|---------|-------|--------|
| A. Только `ingestion_external_keys` + CLI exit code | Уже есть | Нет аудита, времени, diff |
| B. Таблица `ingestion_runs` (started_at, source, bundle_ref, status, report JSON) | Аудит, поддержка | Доп. миграция и UI/ops |
| C. Внешний лог (файл, OpenTelemetry) | Без изменения БД | Сложнее связать с UUID сущностей |

**Рекомендация:** B для production AVL (приёмка, разбор инцидентов); A достаточно для редкого ручного file-import.

### 4.3. Идентичность vs изменяемые атрибуты

| Вариант | Плюсы | Минусы |
|---------|-------|--------|
| A. Strict как сейчас (immutable после create) | Простота, без «тихих» правок | Исправления в AVL требуют нового процесса |
| B. Versioned attributes (history table) | Аудит имён, счётов | Сложность API |
| C. Upsert с политикой «источник прав» | Соответствие AVL | Риск перезаписи без review |
| D. Staging schema → promote после QA | Безопасность | Двойное хранение |

**Рекомендация:** для AVL — **D или B** для матчей/сетов; для справочников (команда, игрок) — **C с whitelist полей** (name, logo) при неизменном external id.

### 4.4. Обновления, конфликты, удаления

| Политика | Когда |
|----------|--------|
| Reject on conflict (текущее) | Пилот, ручной разбор |
| Source wins | Доверенный официальный API |
| Manual review queue | Первые месяцы AVL |
| Tombstone / `cancelled` | Удаление в источнике = смена статуса, не DELETE |

**Рекомендация:** зафиксировать с владельцем AVL матрицу по типам сущностей; в коде — отдельный режим writer, не ломающий strict file-import.

### 4.5. Timezone и время матча

| Вариант | Плюсы | Минусы |
|---------|-------|--------|
| A. Хранить только UTC в `scheduled_at` | Однозначность | Потеря «локального» времени для UI |
| B. UTC + `venue_timezone` или offset на матче | Точные переносы | Нет поля в модели |
| C. Отдельно `scheduled_local_date` (date) + time | Календарь | Дублирование с datetime |

**Рекомендация:** контракт AVL обязан указать формат; минимум — ISO 8601 с offset; в БД — UTC. При необходимости локального отображения — расширение модели (B).

### 4.6. Проверка качества до PostgreSQL

Уровни **разделены по слоям**: ingestion writer не вызывает `evaluate_match_result` (`app/services/match_result.py`); доменная оценка «корректного завершённого матча» применяется в **аналитике** при чтении из БД, а не при записи пакета.

| Уровень | Содержание | Статус в ingestion |
|---------|------------|-------------------|
| L1 | Структурная валидация: парсинг JSON, Pydantic `ImportBundleV1`, CLI `validate` | есть |
| L2 | Ссылки внутри пакета, правила статусов/сетов на уровне схемы; при `import` / `--dry-run` — strict writer: external keys, `data_conflict`, slug/natural key, согласованность полей и сетов с уже записанными строками | есть |
| L3 | Доменный результат матча: `evaluate_match_result` (победитель, непрерывность сетов и т.д. — см. `match-result-validity.md`) | **не** в `app/ingestion/`; используется сервисами аналитики |
| L4 | Сверка с предыдущим снимком AVL | новое (для live-источника) |
| L5 | Квоты и полнота сезона | новое |

**Рекомендация:** для AVL pipeline — L1–L2 оставить на пути writer; **отдельно решить**, нужен ли обязательный gate на L3 до commit (отчёт/блокировка), без автоматического включения evaluator в writer. L4–L5 — в «validation report» с блокировкой commit при согласовании.

### 4.7. Идемпотентность и частичный сбой

| Текущее | Риск |
|---------|------|
| Один transaction на пакет | Большой пакет — долгий lock; откат всего при одной ошибке |
| Повторный import — skip | Безопасно |
| Нет chunking | AVL full-season sync может быть тяжёлым |

**Рекомендация:** обсудить **пакеты по сезону/дате**; опционально savepoints per entity type; для sync — watermark (`last_successful_sync_at`) в `ingestion_runs`.

## 5. Открытые вопросы к владельцу AVL

1. Есть ли **машиночитаемый контракт** (OpenAPI, GraphQL schema, выгрузка JSON/CSV) и его версия?
2. **Аутентификация и окружения** (sandbox/production), выдача credentials, срок жизни, ограничения по IP.
3. **Идентификаторы**: перечень сущностей с внешним id; гарантии стабильности; сценарии merge/split.
4. **Полный перечень полей** по лиге, сезону, команде, игроку, составу, матчу, сету — с семантикой и nullable.
5. **Статусы матча** и жизненный цикл (перенос, отмена, игра в процессе, технический результат).
6. **Часовой пояс** расписания и правила изменения `scheduled_at`.
7. **Исправления данных** задним числом: как узнать, что счёт или состав изменились.
8. **Удаления** в источнике: возможны ли; как отражать в потребителе.
9. **Rate limits**, пагинация, полная vs инкрементальная выгрузка.
10. **Юридическое**: право хранить копию в PostgreSQL, показывать в коммерческом/некоммерческом продукте, атрибуция, срок хранения.
11. **Обезличенный или разрешённый sample** для разработки и автотестов.
12. **Соответствие** нашим правилам валидности матча — кто «источник правды» при расхождении.

## 6. Блокеры реализации

1. **Нет подтверждённой спецификации AVL** (URL, auth, поля, идентификаторы).
2. **Нет согласованного образца данных** и правил mapping внешних id.
3. **Нет политики обновлений/удалений** — текущий strict writer не подходит для живого источника без доработки.
4. **Нет модели `data_origin`** — UI/API не различают demo, file-import и AVL.
5. **Нет журнала импорта** — слабая операционная приёмка.
6. **Нет правового разрешения** на копирование и отображение.
7. **Коллизии natural keys** (`slug`, `demo_slug`, `(league_id, season name)`) при смешивании demo и AVL в одной БД — нужна стратегия namespace (префиксы slug, отдельная БД для prod).
